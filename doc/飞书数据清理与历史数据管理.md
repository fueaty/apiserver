# 飞书数据清理与历史数据管理

## 问题背景

在使用飞书多维表格存储采集数据时，遇到了 `RecordExceedLimit` 错误。

> **⚠️ 重要更正（2026-09-12）**
>
> 本文档早期版本把飞书单表上限写成了「通常为 10 万条记录」，这是**错误的**。
>
> 依据飞书开放平台错误码表，真实限制为：
>
> | 错误码 | 含义 | 限制 |
> |---|---|---|
> | `1254103` | `RecordExceedLimit` | **单个数据表 20,000 条记录** |
> | `1254104` | `RecordAddOnceExceedLimit` | 单次写接口操作记录数上限（500 条） |
> | `1254291` | `Write conflict` | 同一数据表并发写冲突 |
>
> 因为沿用了 10 万这个错误上限，`smart_cleanup.py` 把阈值定成了
> 80,000 / 95,000 / 100,000，导致该脚本永远不会触发清理
> （注：该脚本**并不在 crontab 中**，属于潜在缺陷）。
>
> 而线上清理任务持续失败的**真正原因**是另一回事：删除记录接口
> `records/batch_delete` 的请求体被写成了对象数组
> `{"records": [{"record_id": "..."}]}`，而官方文档要求的是**字符串数组**
> `{"records": ["..."]}`，因此每一批删除都被返回 `HTTP 400 Bad Request`。
> 最终结果是「识别出 19,823 条过期记录、成功删除 0 条」，表格长期卡在
> 20,000 条上限，采集写入持续报错：
>
> ```
> ❌ 采集任务执行失败，创建记录到飞书多维表格异常: RecordExceedLimit
> ```
>
> 本次已修正请求体格式、阈值来源与清理逻辑，详见文末「故障复盘」。

## 容量限制的唯一事实来源

所有容量常量集中在 **`app/services/feishu/limits.py`**，任何脚本都不得再写死数字：

| 常量 | 值 | 说明 |
|---|---|---|
| `TABLE_RECORD_LIMIT` | 20,000 | 单表硬上限（1254103） |
| `BATCH_WRITE_LIMIT` | 500 | 单次写接口上限（1254104），写入/删除均按此分片 |
| `RETENTION_DAYS` | 25 | 保留窗口（天），「飞书表保留多久」的唯一事实来源 |
| `DAILY_BUDGET` | 630 | 日采集预算（条/天），容量守卫（`_assert_capacity_budget`）的算术输入 |
| `WATERMARK` | 17,000 | 安全水位线，清理目标值（留 15% 余量） |
| `WARNING` | 18,500 | 告警水位线 |
| `LIST_PAGE_SIZE` | 500 | 分页读取上限 |

> `limits.py` 在 import 期执行 `_assert_capacity_budget()`：一旦
> `RETENTION_DAYS × DAILY_BUDGET > WATERMARK`，或 `WATERMARK < WARNING` 不成立，
> 或 `WARNING ≥ TABLE_RECORD_LIMIT`，会**直接 `raise ValueError` 让进程起不来**
> （不是 warn）。这是有意为之——历史上正是常量静默超限，表格才卡死数月无人察觉。

### ⚠️ 保留窗口与上限的算术关系（必须理解）

单表 20,000 条是硬上限。**启用 thepaper 站点后**本项目采集速率约 **630 条/天**
（8 个既有站点实测 251 条/轮 × 2 轮 = 502 条/天，thepaper 硬上限
`MAX_RESULTS`=100 条/轮 × 2 轮 = 200 条/天；`limits.py` 取 630 作为有界近似）：

| 保留天数 | 需要的记录数 | 20,000 条的表能否装下 |
|---|---|---|
| 20 天 | ~12,600 | ✅ 可以 |
| **25 天（项目现行策略）** | **~15,750** | ✅ **落在水位线（17,000）以内，首选** |
| 90 天 | ~56,700 | ❌ **装不下** |

**项目策略：飞书表只保留最近 25 天内的数据**（唯一事实来源
`limits.RETENTION_DAYS`；`script/cleanup_feishu_data.py` 的 `--days` 默认值取自它，
`script/scheduled_cleanup.sh` 不再写死天数）。
25 天 ≈ 15,750 条 ≤ `WATERMARK`(17,000)，落在安全水位线以内，两者互为兜底：

> ⚠️ **不粉饰的代价**：保留窗口由 35 天收紧到 25 天、水位线由 14,000 抬到 17,000 后，
> 相对 20,000 条硬上限的**安全余量从 30% 压缩到 15%**。这是新增 thepaper 站点的
> 真实代价——采集量上升，能"兜底"的空间被吃掉一半。**请勿再假设还有 30% 缓冲。**

- 按时间清理负责"不要存太久"
- 按容量清理负责"绝不超限"（即使某天采集量暴增也不会写不进去）

**结论：`--days 90` 这种大跨度在 20,000 条的表里数学上不成立。**
一旦采集长期失败（表写满 → 写不进 → 数据不再更新），表里所有数据都会"过期"，
此时执行大跨度 `--days` 会**把整张表删光**。2026-09-12 就真实出现过这种情况
（当时表内 14,000 条，最早 2026-05-01、最晚 2026-06-04，全部早于 90 天截止线）。

**因此：**

1. 日常维护（cron）按 `limits.RETENTION_DAYS`（25 天）保留，时间清理 + 容量兜底双保险。
2. 时间清理带 **50% 保护闸**（`cleanup_table(guard_ratio=0.5)`）：要删的比例
   超过全表一半时**拒绝执行时间清理**并告警，只做容量清理。
   这是为了拦"历史积压数据首次清理"和"采集长期失败导致全表过期"这两种情况
   ——需要人工加 `--force` 才真删。
3. 若要长期保留 90 天以上，需要**扩容表档位**（专业版 20,000 / 旗舰版 50,000）
   或改为归档到 `history_data/` + 数据库，而不是靠这张表。

> 另：`history_data/` 归档目前截止 **2026-06-01**，而表中还有 2026-06-02 ~ 06-04
> 共约 973 条未被归档。若将来要清空这张表，请先补归档，否则会丢这段数据。

### 2. 飞书表格数据清理机制

#### 2.1 智能清理脚本 (`smart_cleanup.py`)

**功能特点：**
- **容量驱动**（不再按写死的记录数阈值判断）
- 一次全表扫描，按「先时间、后容量」两段式清理
- 今日采集的数据最后才删；仅当非今日数据不足以腾出空间时才回退删除，并明确告警
- 支持 `--dry-run` 预演，上线前可先看清理规模

**清理决策：**
1. 按时间：删除 `collected_at` 早于 `--days` 的记录（`--days` 默认 = `limits.RETENTION_DAYS` = 25 天）
2. 按容量：若「剩余 + 本次待写入」超过水位线（17,000），从最旧的记录开始删到水位以内

**使用方法：**
```bash
cd /root/apiserver
# 仅容量清理，压到水位线以下
PYTHONPATH=/root/apiserver python script/smart_cleanup.py

# 先按时间清理，再按容量兜底
PYTHONPATH=/root/apiserver python script/smart_cleanup.py --days 90

# 上线前预演：只统计不删除
PYTHONPATH=/root/apiserver python script/smart_cleanup.py --dry-run

# 指定表（默认 headlines）
PYTHONPATH=/root/apiserver python script/smart_cleanup.py --table headlines
```

#### 2.2 定时清理脚本 (`scheduled_cleanup.sh`)

**功能特点：**
- 每天凌晨2点自动执行
- 调用 `cleanup_feishu_data.py --table headlines --batch-size 500`
  （**不再传 `--days`**：保留天数由 `limits.RETENTION_DAYS` 决定，默认 25 天）
- **保留策略：只保留最近 25 天内的数据**（唯一事实来源 `limits.RETENTION_DAYS`）
- 时间清理 + 容量兜底双保险；50% 保护闸防误清空
- 记录执行日志（`logs/cleanup_YYYYMMDD.log`）
- 企业微信通知执行结果

**定时任务配置：**
```
0 2 * * * /root/apiserver/script/scheduled_cleanup.sh
```

**调整保留天数**：改 `app/services/feishu/limits.py` 里的 `RETENTION_DAYS` 即可
（唯一事实来源，`scheduled_cleanup.sh` 与 `cleanup_feishu_data.py` 都从它取，不再有 `DAYS=` 硬编码）。
但请注意上限约束——按 630 条/天，20,000 条只够约 31 天，**不要调到 90 天**。

#### 2.3 手动清理脚本 (`cleanup_feishu_data.py`)

**功能特点：**
- 支持自定义保留天数（`--days`），默认 = `limits.RETENTION_DAYS`（25 天）；只想做容量清理可在代码里以 `days_to_keep=None` 调用
- **容量兜底**：即使 `--days` 命中 0 条，也会在超出水位线时从最旧记录开始删
- **50% 保护闸**：时间规则要删的记录超过全表一半时拒绝执行，需 `--force` 才真删
- 支持 `--dry-run` 预演
- 详细的过程日志 + 企业微信通知

**使用方法：**
```bash
cd /root/apiserver

# 按项目策略清理（保留 limits.RETENTION_DAYS = 25 天）—— 先预演
python script/cleanup_feishu_data.py --table headlines --dry-run
python script/cleanup_feishu_data.py --table headlines

# 首次清理历史积压：时间规则要删的比例超过 50% 时会被保护闸拦住，
# 确认无误后加 --force 放行
python script/cleanup_feishu_data.py --table headlines --dry-run
python script/cleanup_feishu_data.py --table headlines --force

# 同时执行数据备份
python script/cleanup_feishu_data.py --backup
```

> 注：`--batch-size` 保留仅为兼容旧调用，实际分片大小由飞书接口上限
> （500 条 / 次）决定，传更大的值无效。

#### 2.4 写入链路自愈（`feishu_service.py`）

清理是「事前」保障，但清理与写入之间仍可能被并发写顶到上限。因此在**所有批量写入的唯一收口**
`FeishuService.batch_add_records()` 内置了兜底：

1. **分片提交**：按 `BATCH_WRITE_LIMIT`(500) 分片，片间 sleep 0.3s，规避 1254104 / 1254291
2. **超限自愈**：一旦命中 `1254103`，自动执行一次容量清理，再把**剩余未写入**的记录重试一遍
3. **不误报**：分片失败时会把已成功写入的记录一并返回，调用方不会把「部分成功」当成「全部失败」

另外 `collection_pipeline.py` 在写入前会调用 `ensure_capacity(incoming=N)` 主动腾空间
（做一次全表扫描），与写入层自愈形成双层保护。

## 注意事项

1. **权限配置**: 确保飞书应用具有足够的API权限
2. **网络稳定性**: 清理过程需要稳定的网络连接
3. **执行时间**: 大量数据清理建议在业务低峰期执行
4. **监控告警**: 关注企业微信通知，及时处理异常情况
5. **`collected_at` 格式**: 容量清理依赖该字段排序。若日志出现
   「`collected_at` 无法解析」，说明该字段格式变了，此时这些记录会被当作
   「最旧」优先删除，**必须先确认格式再执行清理**。
6. **上限不是可调参数**: 20,000 / 500 是飞书平台的硬限制，
   只能在 `limits.py` 里维护，业务代码不要重新定义或调大。

## 故障复盘（2026-09-12）

**症状**：采集任务持续报 `❌ 采集任务执行失败，创建记录到飞书多维表格异常: RecordExceedLimit`

**生产实测证据**（`logs/cleanup_20260912.log`）：

```
处理第 1/40 批，共 500 条记录...
   ❌ 第 1 批删除异常: Client error '400 Bad Request' for url '.../records/batch_delete'
...（40 批全部 400）
8. 清理结果:
   成功删除: 0 条记录
   删除失败: 19823 条记录
```

**根因（按贡献度排序）**：

| # | 根因 | 位置 | 说明 |
|---|------|------|------|
| **1** | **`batch_delete` 请求体格式错误** | `cleanup_feishu_data.py`、`smart_cleanup.py` | 发的是一批**对象** `{"records":[{"record_id":"rec.."}]}`，而官方文档中 `records` 的类型是 **`string[]`**（示例 `["recwNXzPQv"]`）→ 每批都被 400 拒绝。**这才是"清理不生效"的真正原因**：脚本跑得好好的，19,823 条也识别对了，就是删不掉 |
| 2 | **未按 500 分片** | `batch_add_records`、管道内联删除 | 飞书单次写/删上限 500 条（`1254104`），一次性提交全量 id 必然失败 |
| 3 | **阈值写错（潜在）** | `smart_cleanup.py` | 把上限当作 100,000，阈值定成 80,000/95,000 → 该脚本永远不清理。**注意：它并不在 crontab 里**，属于潜在 bug 而非本次直接原因 |
| 4 | **写入无自愈** | `batch_add_records` | 表满后写不进去只能靠人工清理，没有兜底 |

**修复**：

- `delete_records` 统一为 `{"records": ["rec1", "rec2"]}`（纯字符串数组），并在代码里写明"不要改成对象数组"
- 写入 / 删除全部按 `BATCH_WRITE_LIMIT`(500) 分片，片间 sleep 0.3s（规避 `1254291`）
- 管道内联的两处删除也收敛到 `delete_records`，不再自己拼 payload
- `batch_add_records` 内置超限自愈：命中 `1254103` → 清理 → 重试剩余
- 清理改为容量驱动（`smart_cleanup.py` 阈值纠错 + `cleanup_feishu_data.py` 增加容量兜底）

**预防**：

- 回归测试新增断言「请求体 `records` 必须是纯字符串数组」，锁死这个坑
- `limits.py` 集中管理上限，消灭散落的魔数

2. **压缩存储**: 对历史数据进行压缩以节省存储空间
3. **自动化报告**: 生成定期的数据统计和趋势分析报告
4. **多级存储**: 考虑将超长期历史数据迁移到其他存储系统
5. **容量缓存**: 目前每次容量判断都要全表扫描（20,000 条 ≈ 40 次请求），
   可考虑落地本地计数缓存减少扫描
